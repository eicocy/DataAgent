# V2.0.6 可靠性与错误诊断

## 实施范围

基于 V2.0.5 / `fd45ed7`，沿用现有单实例监督器、固定数据版本、注册工具、Artifact 和报告链路。新增可靠性修复，不加入答案流式输出、分布式任务队列或跨重启续算。

- 普通聊天、意图识别、规划共享最近六条消息、最近 4000 字摘要和结构化分析条件；筛选与维度兼容新旧参数。模型提出 ContextPatch，由固定版本字段和参数校验后使用；明确统计问题不再仅因缺少模板关键词而澄清。
- 模型单次默认 90 秒，总分析预算保持 FAST 60 / STANDARD 180 / DEEP 600 秒；解析 120 秒、手动报告 300 秒。子进程、模型和工具共用执行截止时间，调用受剩余时间约束，预留 2 秒终态保存。SDK 不隐式重试超时；计划结构纠错最多一次。自动报告沿用原分析预算。
- HTTP 错误 `data.error_info` 与任务 `error_info` 统一为前端 `Error.info`。原因区分模型/工具/总预算超时、服务中断、鉴权、限流、连接、校验与未知异常；保留旧错误码。关联请求编号不同于分析幂等编号。
- 迁移 `0013_error_diagnostics` 为 AnalysisRecord 和 BackgroundJob 添加可空 JSON 字段，不改写历史失败。详情仅含明确的错误原因、建议、阶段、操作、耗时、阈值、规则、编号和已保留成果；不含凭据、原始行、提示词、SQL 参数或完整模型输出。
- 前端 Options API 错误面板默认摘要、展开详情、复制诊断，失败时可手动复制。接入聊天/步骤/历史/解析/报告；浏览器请求超时仅表示状态未确认，重新连接使用原幂等编号。终态显式重试创建新分析。显示中文操作步骤和本轮固定分析范围。

## 验收要求

先离线回归：上下文最新信息、筛选替换/清除/版本切换、明确统计路由、阶段/总预算故障注入、终态幂等、成果与租约、校验信息与敏感数据排除、迁移保留旧记录。前端验证详情、复制失败、刷新恢复、请求超时与重试，执行构建与关键浏览器流程。

随后只执行一次真实模型工作流：使用原 `movies.csv` 固定版本统计总数，按 genres 原始字段分组展示前十组并绘图，不拆分类型字符串。记录结果与调用次数、耗时；不自动重复调用。复用保存成果导出并打开 PDF/DOCX/XLSX 各一个，不追加模型分析。

## 人工测试入口

### 失败反馈后的补修

用户指出真实页面仍然失败后，追加离线复现确认：合法的 groupby_aggregate 按自身生成的计数字段排序，会被 PlanValidator 错当作原始列校验，触发 COLUMN_NOT_FOUND。现已按实际执行语义区分输入字段与聚合输出排序字段；未知原始字段和未知输出字段仍会拒绝。

另发现 Top N 不能用 DataInput.limit 代替：limit 仅是预览，图表仍读取完整结果。规划入口现按排名需求提供已有 top_n/bottom_n 工具，提示模型先真正选择 N 行再引用绘图；原始列明确使用内部 name。

在原 Dataset 4 / Version 4 的 9125 行数据上，以固定规划和固定解释器运行离线回归：overview、genres_count、top10、chart 四个计算步骤全部成功，生成一份柱状图，前十组与独立 Pandas 计算一致（Drama 1170、Comedy 809、Comedy|Drama 425）。离线报告未生成完整自然语言解释，仍为 partial；该结果仅证明规划校验和计算/绘图路径，不是一次新的真实模型成功验收。未修改记录 8，也没有追加付费模型调用。证据保存在 `tmp/v206-acceptance/offline-movie-regression.json`。

- 打开失败会话，检查原因摘要与建议，展开“查看详细原因”，核对错误码、阶段、阈值、耗时和请求关联编号；复制后不应出现凭据、提示词或数据行。
- 刷新页面后应恢复相同诊断。历史记录缺少字段时显示“未记录”，不将推测当作历史事实。
- 浏览器离线或接口等待超时后点击“重新连接确认状态”，不得重复创建同一分析任务；取消导航不弹任务失败。
- 数据分析追问分别检查：替换地区、保留年份、只清除地区，以及 OR 筛选。核对“当前分析范围”中的逻辑与固定版本。
- 验证真实模型是否能完成电影分析仍需后续单独验收；本轮没有自动反复请求模型来获取成功结果。

### 会话 5 的可操作诊断补修（2026-10-18）

用户随后手动提交的记录 13、14 是 partial：计数等计算完成，generate_chart 失败。将保存计划在原 Dataset 4 / Version 4 上离线重放，确认 top_n 使用 group_by=[genres]，是在每个已汇总类型组合内各取 10 条；每组原本只有一条，输出仍为 902 条。绘图拒绝超过 500 点的数据，但旧 Registry 将具体 ValueError 转成 TOOL_CALCULATION_FAILED，丢失原因。记录 14 的备用聚合仅设置预览 limit=10，完整结果仍为 902 条，同样失败。这些失败与字段缺失、字段长度及上下文上限无关。

修复：绘图的来源为空、字段缺失、类型不符、点数/系列/饼图限制采用结构化工具错误；公开诊断包含安全的实际值和上限。HTTP 和工具 Schema 校验将 missing、string_too_long、类型/数量/范围错误转为中文字段路径和处理说明，不返回原输入。上下文容量不足记录缩减后的实际字符数与 60000 字符上限；模型服务明确返回 context_length_exceeded 时单独分类。计划校验补充类型不匹配字段；明确“前 N 组”却按已汇总维度组内排名的计划进入原有最多一次纠错，不改变每组排名工具语义。

ErrorInfoPanel 默认展示醒目的错误类别、具体原因、如何处理及保留成果；技术信息折叠，省略空白条目。旧 COLUMN_NOT_FOUND 可说明不存在字段，但当时未保存字段名的仍标明“字段名未记录”。未知旧工具异常不能凭错误码推测为字段问题。

记录 13、14 的三个失败绘图步骤已通过保存计划复核，补记脱敏诊断 actual_count=902 / max_count=500、diagnostic_source=saved_plan_replay，并保留原错误码、原任务状态、计划、答案和成果。补记前诊断备份、复核结果位于 tmp/v206-acceptance/；没有追加模型请求，也没有把失败历史改为成功。只将原 top_n 的 group_by 改为空列表后，两份保存计划的主图均生成 10 个数据点；这是离线复核，不能记作完整真实模型验收通过。
