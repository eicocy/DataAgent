# AI Workspace 升级 Phase 2

本文件对应 `docs/UPGRADE_PLAN.md` 的新版 Phase 2，区别于旧版 `docs/phase2.md` 的通用计算工具交付。开发基线为 `7f1e0a5` / `V2.0.1`，仅增量实现领域策略、规划与执行编排，不进入 Phase 3—5。

## 已交付能力

- 105 个版本化 AnalysisProfile 持久化到 `analysis_profiles`。模板表达关注点、指标、工具偏好及报告结构；Planner 根据实际字段和已注册能力生成不同计划。规划中模板不能执行。
- AnalysisTemplateRouter 接受显式选择，或按业务问题自动组合最多三个 Profile。置信度低于 0.75、指标或时间不明确、能力未开放时请求澄清。
- Metric/Dimension Detector 利用列名、类型、基数和值域形成候选。Revenue、GMV、销量、利润分开识别；数值 ID 不自动当金额。`sales` 保持歧义，允许用户明确修正。
- Session 语义映射按 DatasetVersion 隔离，优先级为用户修正、已确认映射、候选。前端“确认字段含义”和明确的自然语言修正均可保存；已排队任务使用提交快照。
- Plan 3.0 固定最多十个授权输入版本，保留逻辑别名、Profile/语义快照、深度预算、依赖及探索关系。历史 Plan 1.0/2.0 读取与旧请求仍兼容。
- TaskGraph 校验循环、工具权限、参数、输出类型、输入别名和结果引用。公共根步骤按数据版本、工具、规范参数与语义版本去重；不同数据集的同名字段不会混用类型。
- 最多两个明确声明安全的规范只读工具并行，每个任务使用私有 DataFrame；主线程统一校验、持久化和发事件。SQL、旧 Adapter、模型调用及写入仍串行。
- DEEP 模式允许由已验证结果触发新节点，受节点、探索深度、模型调用、Token 和时间限制；新增计划再次校验。失败恢复保留已完成节点及必需任务，可靠性、安全和持久化失败不交给模型绕过。
- Composer 开放实际可用模板、深度和服务端配置的模型；会话附件可选为额外输入。执行详情显示依赖、数据别名、探索来源和耗时。刷新与网络重试保留完整请求选项。

## 服务端预算

| 模式 | 最大节点 | 探索深度 | 模型调用 | 分析期限 | Token 预算 |
|---|---:|---:|---:|---:|---:|
| FAST | 6 | 0 | 6 | 60 秒 | 20,000 |
| STANDARD | 16 | 0 | 10 | 180 秒 | 60,000 |
| DEEP | 32 | 3 | 16 | 600 秒 | 120,000 |

每次模型调用前保守预留输入和输出预算，供应商未返回用量时不释放估算。预算不足、依赖失败和无法验证的探索保留已完成结果，按实际交付返回部分完成。深度不会开放不存在的业务工具。

## API 和数据库

继续使用 `/api/v1` 与当前资源模型。

| 接口 | Phase 2 行为 |
|---|---|
| `GET /workspace/capabilities` | 宣布 Profile 执行、多输入、深度和实际模型能力 |
| `GET /analysis/profiles`、`/{id}` | 版本化策略与真实可用状态 |
| `POST /analysis/runs` | 新增可选 `inputs`、`profile_ids`、`depth`、`category`、`model_id` |
| `GET /analysis/runs/{id}`、Trace、SSE | 返回请求选项、Plan 3.0、Profile 和探索事件 |
| `GET /analysis/sessions/{id}/semantic-mappings` | 当前授权数据版本的候选与修正 |
| `PATCH /analysis/sessions/{id}/semantic-mappings` | 验证列和版本所有权，锁定并刷新 Session 后合并修正 |

同一 `request_id` 的重复请求必须具有一致的完整公开配置；不同深度、输入或模板返回冲突。输入版本在排队前固定，执行和工件证据保存实际输入的 DatasetVersion。

`0010_analysis_profiles` 从 `0009_workspace_reports` 增量新增 `analysis_profiles` 和可空 `analysis_records.request_config_json`；历史记录不回写新配置。Session 映射继续存 `context_json`，不新建 plans/tasks/semantic 表。不修改旧迁移。

## 使用方式

1. 选择或上传数据，按需要将会话附件勾选为额外输入。
2. 输入问题；模板可留自动或手选。选择快速、标准或深度分析。
3. 展开“确认字段含义”，核对有歧义的列并保存；也可以明确输入“sales 字段不是销售额，是销量”。
4. 发送后查看真实任务与工具执行。结果不足会显示澄清或部分完成，不假装完成预测或专业业务归因。

模型选项只允许服务端现有配置。当前仅配置一个模型时只显示该模型；前端不能传入 Key、任意模型地址或 Base URL。

## 验证边界与限制

验证记录见 `UPGRADE_PROGRESS.md`，区分临时 SQLite、隔离 MySQL、模型替身、模拟 API 浏览器和本地服务检查。浏览器模拟流程验证交互，不等同于真实模型端到端验收。

真实 DeepSeek 另以两行模拟 CSV 验证 FAST / 数据质量 Profile：Plan 3.0 的四项只读检查全部完成，事实绑定总结与计算一致。该样例使用隔离数据库和文件目录；不代表全部领域或生产数据均已验收。质量检查被识别为清洗意图时，规划和执行共用只读工具白名单，仍不执行清洗或发布数据版本。

本阶段多输入用于分别分析和对照，跨数据集 Join 尚未开放。销售与财务模板只调用现有通用工具，专业口径、周期比较、贡献分解和预测验证属于 Phase 3；相关模板保留 limited/planned。自动多格式报告、完整 Artifact 引用/长期留存属于 Phase 4；生成 Python 的沙箱属于 Phase 5。现有手动报告功能继续可用。

并行限于受信任的已注册计算，不接受自由 Python。单实例监督器仍只领取一个顶层任务；最终期限由父进程监督器终止工作子进程，不宣称 Python 线程可以强制终止或具备沙箱隔离。
